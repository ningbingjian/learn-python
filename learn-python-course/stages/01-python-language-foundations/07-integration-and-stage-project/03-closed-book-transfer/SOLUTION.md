# 参考解为什么这样分配责任？

请先提交自己的答案。这里解释判断，不要求逐字符一致。

字段在 validation 中分成 parse_due 与 clean_due：CLI 文本可以为空白，需要先转换；模型接收已经转换的值，仍必须拒绝负数、布尔和非整数。用明确的 None 判断保留合法 0，避免 truthiness 吞掉业务值。

Task 构造接收可选 due_in_days。update 先计算字段三元组，再验证截止值，最后才赋值四个属性；因此最后一个字段失败也不会留下前三个字段的新值。edit 是完整替换，None 清除截止；若采用局部更新，必须另行设计“未提供”标记，不能悄悄改变题目。

TaskTracker.by_priority 使用 sorted 与普通 priority_key 函数。sorted 构造新列表，稳定排序保证相同优先级保留原顺序；返回的 Task 仍是相同对象。它不是深复制，也不是历史快照。due_today 选择未完成且截止值恰为 0 的记录，None 和未来天数自然不满足。

CLI 只添加一个输入与两个命令。read_fields 返回四元组后，add/edit 的解包与调用都同步修改；忘记任一调用点会由会话测试发现。显示使用显式 None 分支，而不是 due or "none"。

可接受的替代方案：排序键可用适当的现有工具，筛选可用普通 for 构造新列表，解析错误文案可以不同。不可接受：原地排序正式集合、把 0 当无截止、先改标题再检查截止、为这一字段引入继承或第三方框架、删除旧命令测试掩盖回归。

验收并不要求参考解的测试数量；它要求题面中的每一种行为有证据。作者的参考测试只能验证参考实现，真实学习者的设计解释与独立完成记录仍需另行收集。
