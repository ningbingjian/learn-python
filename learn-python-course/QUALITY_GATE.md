# Course Quality Gate v3.0

> 目的：防止课程退化为“模板化 README + 可运行小 Demo”，同时保证理论、正文、源码、工程边界、演进关系和学习验证一致。

## 1. 三层质量门禁

```text
Technical Gate
→ Teaching Gate
→ Learning Gate
```

技术正确只是第一层。代码能运行、测试能通过，不代表课程已经教会了人。

## 2. Technical Gate

适用于含代码、命令、实验、数据或性能结论的内容。

### 2.1 基本可重复性

- [ ] Python / Framework / Database 等版本基线明确。
- [ ] README 中的运行命令可以实际执行。
- [ ] 预期输出、异常和真实结果一致。
- [ ] 环境可以通过文档恢复。
- [ ] 依赖与锁文件策略符合当前工程边界。
- [ ] macOS、Linux、Windows 差异已说明或确认不影响结论。

### 2.2 源码与测试

- [ ] 当前 README 对应的源码能运行。
- [ ] 自动化测试稳定，不依赖执行顺序和偶然网络状态。
- [ ] 所有正式保留的演进状态都被验证，而不是只验证最终版本。
- [ ] 测试断言行为和契约，不只断言一段脆弱输出文本。
- [ ] 测试证明范围被准确描述。
- [ ] 示例中故意保留的失败状态有明确运行方式和预期失败证据。

### 2.3 Python 工程边界

- [ ] `pyproject.toml` 只在真实项目、Package、Application 或独立依赖边界需要时出现。
- [ ] 没有为每个 API 复制相同的 project 配置。
- [ ] Module 根项目、独立项目或 uv workspace 的选择有理由。
- [ ] workspace member 的依赖声明没有因为共享环境而“碰巧可用”。
- [ ] 早期教学状态没有提前获得后续 Framework 依赖。
- [ ] `uv.lock`、dependency group、optional dependency 和 build backend 使用符合当前阶段知识边界。
- [ ] Package import、CLI entry point 和 src layout 在适用时经过验证。

### 2.4 代码质量

按当前 Stage 要求检查：

- [ ] Ruff / formatting 通过。
- [ ] Pyright 或 Mypy 通过，或明确记录当前允许的类型缺口。
- [ ] pytest 通过。
- [ ] 异常、资源释放和优雅关闭经过验证。
- [ ] 没有隐藏依赖本机状态、固定绝对路径、秘密或不可复现外部服务。

Technical Gate 通过不等于 `VALIDATED`。

## 3. Teaching Gate

### 3.1 核心问题与能力目标

- [ ] Unit 对应一个真实问题、机制或能力闭环，不只是一个 API 名称。
- [ ] 学完以后能做什么明确。
- [ ] 为什么现在学习清楚。
- [ ] 前置能力真实且具体。
- [ ] 不属于当前阶段的深层内容被合理后置。

以下情况直接退回：

```text
标题只是 int / append / decorator
但没有说明它们解决什么问题、形成什么能力
```

### 3.2 书籍式正文

- [ ] 正文主要篇幅用于理论、机制、代码因果、设计边界和工程实践。
- [ ] 章节可以连续阅读，不像任务卡或文件点击导航。
- [ ] 标题表达技术问题，不机械使用 Step / Checkpoint / Snapshot。
- [ ] 操作步骤只在 BUILD / OPS 等确实需要时出现。
- [ ] 删除模板话术后仍然有足够技术密度。

### 3.3 理论深度

核心概念至少回答：

- [ ] 是什么。
- [ ] 为什么出现。
- [ ] 解决什么问题。
- [ ] 与相邻概念什么关系。
- [ ] 当前代码、系统或现象中如何体现。
- [ ] 代价、失败模式和边界是什么。
- [ ] 什么情况下不应使用。

不要求每个入门知识都进入 CPython 源码；深度必须与当前问题和阶段匹配。

### 3.4 因果链

- [ ] 上一状态的问题能够自然引出当前知识。
- [ ] 新抽象不是从最终架构倒灌。
- [ ] 代码变化与理论变化互相解释。
- [ ] 学习者能看见“不引入它时会怎样”。
- [ ] 主线项目没有为了覆盖知识清单强行加入不相关功能。

### 3.5 文档与源码一一对应

- [ ] 当前 README 讲的就是当前目录源码。
- [ ] 当前目录保存正文结束后的完整状态。
- [ ] 不需要 checkout commit 才能获得对应代码。
- [ ] 不需要从最终版本反推中间状态。
- [ ] README 提到的文件和命令真实存在。
- [ ] 源码中的重要职责都在正文中有解释。

### 3.6 演进关系

如果当前章节基于上一状态：

- [ ] 明确基于哪个目录。
- [ ] 说明上一版本具备什么。
- [ ] 说明为什么不够。
- [ ] 说明修改哪些文件、职责和行为。
- [ ] 展示必要 Before / After 或 diff。
- [ ] 当前目录保留演进后的完整状态。
- [ ] 上一完整状态仍然保留。
- [ ] 下一章节可以明确基于当前状态继续。

任何一项需要靠猜、作者口头解释或 Git 历史才成立，都不通过。

### 3.7 是否应该新建源码状态

- [ ] 新目录代表数据模型、责任、机制、测试或行为的显著变化。
- [ ] 不是一个小 API 就复制完整工程。
- [ ] 纯理论没有伪造源码。
- [ ] 独立 Example / Project 有独立理由。
- [ ] Focused Lab 真的需要隔离变量。
- [ ] 不机械执行“永远复用”或“永远新建”。

### 3.8 Source Ownership

- [ ] 教学源码属于真正讲解它的 Unit。
- [ ] Focused Lab 位于所属 Unit 内。
- [ ] Module Project 由负责综合验收的 Unit 承接。
- [ ] Stage Project 有明确归属。
- [ ] Module 顶层没有无说明的 `app/`、`labs/`、`project/`、`units/` 包装或副本目录。
- [ ] 删除一层包装后若不影响归属理解，应优先删除。

### 3.9 Python 工具没有压过知识主线

- [ ] 入门正文不会每课重新解释 uv、pytest 和目录创建。
- [ ] 尚未系统学习 Packaging 时，只解释运行当前项目所需部分。
- [ ] 高级阶段不机械重讲基础命令，而解释当前 Package / workspace / deployment 边界。
- [ ] 自动验收工具不会占据核心概念的大部分注意力。
- [ ] 第一次程序不会因为 Bytecode、GC、GIL 等后续内容失焦。

### 3.10 Progressive Depth

- [ ] Must 主线可以独立形成当前能力。
- [ ] Should 内容服务高频工程边界。
- [ ] Expert 内容服务当前问题，而不是展示术语。
- [ ] 后续 Stage 有更自然位置的内容没有提前完整展开。
- [ ] 深度标签没有把正文切成碎片化阅读路径。

### 3.11 错误、反例和边界

- [ ] 反例代表真实误用，不是人为玩具错误。
- [ ] 失败可以观察、推导或通过证据定位。
- [ ] 修复解释了原因，而不是只替换代码。
- [ ] “常见误区”没有机械复制相同清单。
- [ ] 安全、并发、事务和分布式内容包含负面测试或 Failure Mode。

### 3.12 练习与迁移

- [ ] 练习明确基于哪个完整源码状态。
- [ ] 练习提供新需求、约束和验收标准。
- [ ] 不能只通过修改常量或照抄正文完成。
- [ ] Solution 不仅给代码，还说明判断过程。
- [ ] Module / Stage Project 真正组合能力。

### 3.13 信噪比

以下情况直接退回：

- 大量重复“打开这个文件”“只记住一句”。
- 每一课完全相同的章节模板。
- README 很长，但技术内容很薄。
- 每个小知识都固定有 Challenge / Mastery Check，却没有真实迁移。
- 代码只有几十字节，包装和脚手架却占据主要学习成本。
- 为了显得深入，在入门阶段堆运行时和源码名词。

## 4. Teaching Type 专项门禁

### 4.1 MECHANISM

- [ ] 有预测。
- [ ] 主要变量被隔离。
- [ ] 观察结果可以支持结论。
- [ ] 从现象推导机制，而不是先公布答案。
- [ ] 边界条件被验证。

### 4.2 FAILURE

- [ ] 有真实症状和至少两个合理假设。
- [ ] 证据用于排除。
- [ ] Root Cause 与证据一致。
- [ ] 修复后有回归。
- [ ] 有防复发措施。

### 4.3 SOURCE

- [ ] 固定版本。
- [ ] 有最小触发入口。
- [ ] 断点、调用栈和关键状态与外部现象连接。
- [ ] 说明为什么进入下一方法或分支。
- [ ] 区分稳定契约和实现细节。
- [ ] 不是逐行翻译源码。

### 4.4 PERFORMANCE

- [ ] 指标和目标明确。
- [ ] workload / dataset / environment 可复现。
- [ ] 有 baseline。
- [ ] 有 profile / metric / trace 支撑瓶颈判断。
- [ ] 主要变量改变清楚。
- [ ] 优化后重新测量。
- [ ] 同时讨论收益、副作用、资源和成本。
- [ ] 不用一次 benchmark 或脆弱毫秒阈值下结论。

### 4.5 DESIGN

- [ ] 约束明确。
- [ ] 至少两个可行方案。
- [ ] Trade-off 和 Failure Mode 完整。
- [ ] 决策与约束一致。
- [ ] 记录何时需要重新评估。

### 4.6 PROJECT

- [ ] 有用户价值和业务背景。
- [ ] 有技术与范围约束。
- [ ] 里程碑形成自然能力演进。
- [ ] 验收可执行。
- [ ] 有至少一个条件变化任务。
- [ ] 项目没有为了组件数量牺牲清晰度。

## 5. Learning Gate

达到 `VALIDATED` 至少完成一种真实学习验证；复杂 Unit 通常需要多种。

### A. 从正文跟做

由未参与编写的人按正文从基线完成当前实现或实验，期间不依赖作者口头补充。

### B. 闭卷迁移

给正文未展示的新需求，学习者根据当前模型完成修改并解释判断。

### C. 故障定位

给新的症状和证据，学习者独立建立假设、排除并找到根因。

### D. 理论解释

不照抄原文解释核心模型、边界、代价和相邻概念关系。

### E. 性能分析

给新的 workload，学习者建立 baseline、采集证据、提出修改并复测。

### F. 设计重评估

改变一项关键约束，学习者能够指出原决策是否仍成立，以及架构如何调整。

## 6. 源码演进专项 Review

Reviewer 必须实际走：

```text
上一完整源码状态
→ 当前 README
→ 当前完整源码状态
```

并回答：

```text
演进前是什么？
为什么需要变化？
具体怎么变？
测试怎样证明？
当前目录是否正好是改完后的结果？
下一章节能否明确以它为基线？
```

## 7. 路径、链接和状态一致性

- [ ] README 中相对链接有效。
- [ ] “本节基于”路径存在。
- [ ] CI working-directory 与真实目录一致。
- [ ] 移动或删除后没有旧路径引用。
- [ ] `stages/README.md`、Stage README 和课程 README 状态一致。
- [ ] 没有把 `DESIGNED` 写成 `BUILT`。
- [ ] 没有把 Technical Gate 通过写成 `VALIDATED`。

## 8. 模板污染检查

以下情况直接退回：

- 上一章类名、主题、版本或业务残留。
- 每章完全相同的“常见误区”。
- 一个 API 一个独立项目且无真实边界。
- 为了连续性把独立实验硬塞进主线。
- 为了独立性复制大量相同脚手架。
- workspace 或根项目让早期状态提前获得后续依赖。
- 文档已改路径，测试、CI 和命令仍指旧目录。
- AI 生成的内容有似是而非的源码调用链、性能数字或版本事实。

## 9. AI / Generator Review

适合自动化：

```text
文件列表
链接检查
目录结构检查
格式与 lint
测试执行
类型检查
重复 pyproject 配置检测
状态表一致性
```

必须人工审查：

```text
理论推导
Why 与因果链
源码演进价值
故障根因
性能证据
设计判断
学习迁移任务
生产建议
```

## 10. 状态规则

```text
Technical Gate ✅
Teaching Gate ✅
```

才可以标记 `BUILT`。

只有再通过真实 Learning Gate 才可以标记 `VALIDATED`。

这里的 `BUILT` 指当前 Unit 设计要求的必要材料已完成，不要求每个 Unit 机械拥有 README、源码、Lab、Exercise、Case 和 Project 全套目录。

## 11. 发布前最后检查

发布一个含源码的章节前，作者必须能清楚说明：

> 这篇正文解决什么问题；为什么当前源码正好是讲完后的状态；它基于哪个状态演进；为什么值得保存；运行和测试提供了什么证据。

发布一个 Module 前还必须确认：

> 目录有没有纯包装层；Lab 和 Project 是否归属正确；工程配置是否破坏教学差异；所有链接、命令和 CI 路径是否真实；学习者完成后究竟多了什么能力。
