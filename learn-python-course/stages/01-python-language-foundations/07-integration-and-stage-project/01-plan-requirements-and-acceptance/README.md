## 能用四条命令，不等于可以交付

前六次演进解决了语言与结构问题。现在用户还不能改错别字、删除无用任务，或只看未完成项；关闭输入还会出现 traceback。继续写代码之前，必须决定这些动作准确意味着什么，否则“完成了 edit”只是一个函数名存在。

项目仍是单进程内存应用，退出即丢失数据，不添加文件、数据库或框架。所谓完整，是完整兑现本 Stage 的需求，不是生产级任务管理系统。

## 固定命令词，也固定错误后的下一步

| 命令 | 额外输入 | 成功结果 | 失败后 |
|---|---|---|---|
| add | 标题、优先级、备注 | 新建未完成任务 | 返回命令提示，不消耗 ID |
| list | 无 | 全部，新增顺序 | 空集合显示 No tasks. |
| list --pending / list --done | 无 | 仅对应状态，原顺序 | 空结果显示 No tasks. |
| complete | ID | 完成或告知已完成 | 不存在或非整数均不修改 |
| edit | ID、完整新标题、优先级、备注 | 替换可编辑字段 | 任一输入失败则整体保持原状 |
| delete | ID | 移除目标 | 不存在不改变其他任务 |
| quit | 无 | Goodbye.，退出 0 | 不读取后续输入 |

命令只去首尾空白并转小写；`list  --pending` 中间两个空格并非本版规定命令，按未知命令反馈。这里只做固定词路由，不冒充完整 Shell 参数解析器。

编辑是**完整替换三个可编辑字段**，不是“空值代表保留”。标题仍不可为空；备注空白代表清除为 None；ID 和 done 保持不变。这样读者不用猜空字符串到底是删除还是保留。若未来要局部更新，需要新的缺省标记契约，而不是随意复用 None。

## 删除以后 ID 为什么不能重新编号？

列表位置服务存储顺序；业务 ID 服务稳定引用。已有 #1、#2，删除 #1 后，#2 仍是 #2；下一次新增是 #3。不能把 ID 设为 `len(tasks) + 1`，否则删除中间项或末项后会复用身份。

删除按 ID 找到对象，再从集合移除；不在遍历过程中连续删除多条记录。筛选则只构造返回列表，不改变正式集合。两种操作都可能“让屏幕少一条”，但状态契约相反，测试必须区分。

## 先把编辑失败写成可观察断言

对于已完成任务 #1，原值为 A、优先级 2、备注 old：

```text
edit #1，输入新标题 B，再输入非法优先级 4
→ 标题仍为 A，优先级仍为 2，备注仍为 old，done 仍为 True
```

这能揭露“读到一个字段就立即修改一个字段”的错误。正确顺序是先读完并验证所有输入，再在模型方法里提交。直接 API 调用也必须遵守，不能只靠 CLI 保护。

本章使用“整体保持原状”描述单次同步内存操作，不引入数据库事务术语体系；但先验证后修改的判断可以迁移到后续阶段。

## EOF 和 Ctrl-C 也是产品行为

EOF 表示输入结束，不是非法字段。终端中 macOS/Linux 常用 Ctrl-D，Windows 常用 Ctrl-Z 后回车；脚本管道也会自然结束。最终版输出 `Input ended. Goodbye.`，退出 0。Ctrl-C 输出 `Cancelled. Goodbye.`，退出 130。

若发生在 add 或 edit 的任一输入处，尚未完成的操作不提交。已经成功完成的内存操作不回滚；退出后所有内存数据自然消失。不要捕获所有 Exception 把程序 Bug 当作退出，RuntimeError 等非预期错误仍应暴露。

## 先分配责任，再补功能

Task.update 维护单条任务的字段一致性；TaskTracker.edit/delete/select 维护集合操作；CLI 负责读取和展示；main 负责会话结束策略；__main__ 把返回值变成进程退出码。validation 继续负责字段解析。没有新需求要求新的 Package。

测试按失败原因分层：

- 领域测试：编辑原子性、ID 稳定、筛选不改原集合、对象隔离。
- 会话测试：命令与提示接线、连续输入、空状态、失败后恢复。
- 入口测试：安全导入、真实 EOF 退出与退出码。

测试工具可以使用标准库 subprocess，但正文的能力目标是读懂断言，不要求本阶段实现一套测试框架。
